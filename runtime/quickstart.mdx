Autter Runtime captures errors and usage from your frontend and backend. Compatible server releases also capture structured logs and operation outcomes. This guide sets up capture and checks stored data; follow [Operation logging](/runtime/operation-logging) for the new logging APIs and required deployments.

<Info>
  Prefer to have an AI coding agent set this up for you? See [AI agent skills](/runtime/skills) — `npx skills add Autter-dev/autter-skills --all`, then tell your agent *"install Autter Runtime in this project."*
</Info>

## Concepts

**Two kinds of keys** — never mix them up:

| | Server key | Client key |
| --- | --- | --- |
| Looks like | `autter_rt_…` | `autter_rtc_…` |
| Secrecy | **secret** — env vars only, never in a browser bundle | **publishable** — safe to ship in frontend JS |
| Can send | OTLP traces + metrics + logs, browser events | browser events only (`/v1/browser`) |
| Extra protection | — | per-key origin allow-list, tighter rate limit |

**Two ways to send browser events:**

- **Relay** (recommended, including static sites) — the browser posts to a same-origin route on *your* server, Worker, or edge function, which forwards with your server key. Allow the relay in `connect-src` (usually `'self'`) and check the actual browser request. See [Stack integrations](/runtime/integrations) for the serverless relay.
- **Direct** (lossy fallback for pure-static only) — the browser posts straight to the ingester with a publishable client key. Ad-blockers silently drop these cross-origin requests.

**What is never sent:** cookies, DOM content, form values, request/response bodies, headers, emails, full URLs with query strings.

Use a Runtime ingest key, not an Autter CLI/PAT or MCP token. Keep the key value
in your environment; your coding agent only needs its variable name. Custom
log context is application-authored: do not include sensitive data, even though
the SDK and ingester redact it.

<Steps>
  <Step title="Run the ingester">
    For a local try-out, clone the repo and start ClickHouse plus the ingester with Docker Compose:

    ```bash
    git clone https://github.com/Autter-dev/autter-runtime
    cd autter-runtime
    docker compose up   # ClickHouse + ingester on :4318, key "dev-key"
    ```

    For real deployments, see [Self-hosting](/runtime/self-hosting) or use Autter's hosted ingester at `otlp.autter.dev`.
  </Step>
  <Step title="Instrument your backend">
    ```bash
    npm install @autter/runtime-node@^1.4.0
    ```

    Create `instrument.cjs` — it must load **before** your app:

    ```js
    const { initAutterServer } = require("@autter/runtime-node");

    initAutterServer({
      apiKey: process.env.AUTTER_RUNTIME_KEY,   // server key
      endpoint: process.env.AUTTER_ENDPOINT,     // your ingester URL
      service: "payments-api",
      environment: process.env.NODE_ENV,
      release: process.env.GIT_SHA,              // enables "broke in release X"
      retainTracesAboveMs: 2000,
    });
    ```

    ```bash
    node --require ./instrument.cjs server.js
    ```

    Reuse your existing SDK initialization if you already have one. The example opts into bounded, local slow-request trace retention. Set `GIT_SHA` to the deployed commit SHA. See [Endpoint regressions](/runtime/endpoint-regressions) for metric requirements and retention limits.

    This records HTTP request metrics and captures crashes. For handled errors:

    ```js
    const { captureException } = require("@autter/runtime-node");

    try {
      await chargeCard(order);
    } catch (err) {
      captureException(err, { "order.id": order.id });
      throw err;
    }
    ```
  </Step>
  <Step title="Add server operation diagnostics">
    First [check installed SDK exports and ingestion support](/runtime/operation-logging#check-your-installation).
    Node/Next.js SDK and ingester **1.4.0+** are required; installing a
    package does not establish that the hosted ingester or platform is ready.

    Once supported, add `logging` options to the existing initialization and
    wrap meaningful checkout/job boundaries with `withRuntimeOperation`.
    Record measured steps, bounded nested context, and explicit business
    outcomes. Use `runtimeLogger.info/warn/error` for diagnostics, while
    keeping exception or declared failed-outcome capture for issues.

    [Follow the checkout example](/runtime/operation-logging#record-a-customer-operation).
    A callback that returns normally defaults to success, so declare a failed
    payment result explicitly. Preserve existing loggers and await flushing at
    the end of short-lived jobs. If support is pending, continue basic capture
    and report that gap.
  </Step>
  <Step title="Instrument your frontend">
    ```bash
    npm install @autter/runtime-browser
    ```

    Add a relay route to your backend (the key stays server-side):

    ```js
    // Express
    const { createBrowserRelayHandler } = require("@autter/runtime-node");
    app.post("/api/autter-runtime",
      createBrowserRelayHandler({ apiKey: process.env.AUTTER_RUNTIME_KEY,
                                  endpoint: process.env.AUTTER_ENDPOINT }));
    ```

    Then initialize the tracker in your frontend entry point:

    ```ts
    import { initAutterBrowser, captureException, trackEvent } from "@autter/runtime-browser";

    initAutterBrowser({
      endpoint: "/api/autter-runtime",   // same-origin — no key here
      service: "web-app",
      release: import.meta.env.VITE_GIT_SHA,
    });

    captureException(err, { operation: "start-checkout" }); // handled errors
    trackEvent("clicked_upgrade");                          // usage counters
    ```

    No backend? See the direct setup and full walkthrough in [Installation](/runtime/installation).
  </Step>
  <Step title="Verify data is flowing">
    In a local test environment, trigger a test error, then query ClickHouse. In production, inspect existing traffic instead; do not generate artificial errors or requests:

    ```sql
    SELECT service, error_type, message, route, occurred_at
    FROM autter_runtime.runtime_error_occurrences
    ORDER BY occurred_at DESC LIMIT 10;

    SELECT service, route, sum(request_count) AS requests, sum(error_count) AS errors
    FROM autter_runtime.runtime_metrics_1m
    WHERE bucket_at > now() - INTERVAL 1 HOUR
    GROUP BY service, route;
    ```

    With the local Compose setup: `docker compose exec clickhouse clickhouse-client --password dev`.

    When operation logging is enabled, verify it separately:

    ```sql
    SELECT service, operation, outcome, message, trace_id, operation_id, attributes
    FROM autter_runtime.runtime_logs
    ORDER BY occurred_at DESC LIMIT 10;
    ```

    These queries are for your local development database. In the platform,
    open the intended repository's **Runtime → Logs**, inspect the captured
    IDs, and confirm the failed issue's **Operation evidence**. Logs and traces
    may arrive separately; refresh or rerun analysis for later evidence. An
    unavailable source differs from an available source with no matching rows.
    See [logging verification](/runtime/operation-logging#verify-stored-logs-and-failure-evidence).
  </Step>
</Steps>

## Production checklist

- Server keys only in backend env vars; client keys only where a relay is genuinely impossible.
- Client keys have `allowedOrigins` set to your exact app origins.
- `release` is wired to your git SHA in **both** frontend and backend — it powers regression detection ("broke in release X").
- Keep trace sampling at ~1% (`traceSampleRate`) — errors are always captured regardless.
- Confirm the logging SDK release and ingester/platform deployment separately; redeploy the application after upgrading.
- Declare business outcomes, preserve existing loggers, and check buffered/dropped records and flush failures. Logs are best-effort diagnostics.
- Check export volume after enabling `retainTracesAboveMs`. The platform rollout does not enable this option in existing applications.
- The relay route keeps its built-in per-IP rate limit, or your WAF covers it (`perIpRateLimit: false`).
- Direct browser ingest: your CSP includes `connect-src https://your-ingester…`, and you accept that ad-blockers may drop some events (the relay avoids this).
- The ingester's `/healthz` is wired to your load balancer health check.
