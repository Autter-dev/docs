Install the Autter skills, sign in to Autter from your coding agent, and ask:

> Use the Autter skills to set up Runtime for this project.

The agent checks what your repository needs, creates and stores the Runtime key after you approve it once, instruments every service in any language, and verifies that telemetry arrives. You approve the sign-in and the key, then review, merge and deploy.

[Autter Skills](https://github.com/Autter-dev/autter-skills) are [Agent Skills](https://agentskills.io) for Claude Code, Cursor, Codex and any other coding agent that supports the standard. The agent talks to Autter through the [Autter MCP server](/features/mcp).

<Info>
  Prefer to do it yourself? See [Quickstart](/runtime/quickstart) (npm packages) or [Using Autter Runtime without npm](/runtime/without-npm) (any other language).
</Info>

## Set it up

<Steps>
  <Step title="Install the skills">
    Run this in your project. It needs Node 18 or newer on your machine; the codebase itself does not need Node.

    ```bash
    npx @autter/skills
    ```

    The installer finds the coding agents on your machine, asks before installing, and prints a short summary. It also offers to add the Autter MCP server (`https://api.autter.dev/mcp`) to your project, and yes is the default:

    - It writes `.mcp.json` for Claude Code and `.cursor/mcp.json` for Cursor.
    - It adds an `autter` entry next to your existing servers and never replaces an `autter` entry that is already there.
    - It never writes a key or token. You sign in from the agent in the next step.

    Pass `--mcp` to add the server without asking, or `--no-mcp` to skip it. With `--global`, or `--yes` without `--mcp`, the installer prints the setup instructions instead of writing a file. For other agents, add the server yourself as in [Connect an agent over MCP](/guides/mcp-setup).
  </Step>
  <Step title="Sign in to Autter">
    Open your agent. When it shows **Authenticate** for the `autter` server, click it, then click **Authorize** in the browser and choose your organization.
  </Step>
  <Step title="Ask your agent">
    > Use the Autter skills to set up Runtime for this project.

    The agent runs `autter-runtime-setup` and routes each service to the right language skill. You do not need to pick one.
  </Step>
</Steps>

Other installer options: `--agent claude-code cursor` chooses agents, `--global` installs for your user account instead of the project, `--skill otel-node-style` installs one skill, and `--list` shows the skills first.

Using the open [`skills`](https://github.com/vercel-labs/skills) CLI instead? Run `npx skills add Autter-dev/autter-skills --all`. Recent versions of that tool need Node 22.20 or newer. It installs the skill files only, so add the MCP server as in [Connect an agent over MCP](/guides/mcp-setup).

Runtime setup does not need the Autter CLI. Optional: installing the [Autter CLI](/cli/install) adds who wrote the failing code, an AI agent or a person, to Runtime issues.

## What the agent does

1. **Checks readiness.** It reads your repository's setup checks from Autter: whether the repository is connected, whether the GitHub App can read it, whether a server key exists, whether services report, whether they report a commit and release, and whether source maps arrive.
2. **Creates and stores the key, after one approval.** It asks one question that names the repository, the key kind and every place the key goes: `.env.local` (only when it is gitignored) and your host's secret store when that host's command-line tool is installed and signed in on your machine. The key goes straight into those places without being printed. Afterwards the agent refers to it only by its prefix, such as `autter_rt_ab12…`. If the repository already has a server key, the agent creates none and asks only which environment variable holds it.
3. **Instruments each service** with the matching language skill, and records the instrumentation convention in your repository's agent instruction files, such as `CLAUDE.md` or `AGENTS.md`.
4. **Makes each service report its commit and release**, so Autter can tie an error to the release, commit and pull request behind it. See [Link errors to code](/runtime/link-errors-to-code).
5. **Wires source maps** for built frontends and bundled servers. This asks one more approval, for an upload-only key that goes straight into your CI secrets.
6. **Verifies locally and checks readiness again.** Test events run only in a local or isolated environment. The agent tells you which checks wait for a deploy.
7. **Checks again after you deploy.** Tell the agent you deployed. It checks release health and, for one real issue, the release, its commit, the suspect commits and the pull request. It never creates an error in production to get one.

| Your agent does | You approve once | Only you |
| --- | --- | --- |
| Checks readiness | The Autter sign-in: **Authenticate** in your agent, **Authorize** in the browser | Install the Autter GitHub App and connect the repository, when the agent says it is not connected |
| Creates and stores the Runtime key | Creating the Runtime key | Store the key on a host the agent could not reach: copy `AUTTER_RUNTIME_KEY` from `.env.local` into the host's secret settings |
| Instruments each service and makes it report its commit and release | The source map upload key, for built frontends and bundled servers | Set `AUTTER_COMMIT` to the deployed commit where the service runs, when your platform provides no commit variable |
| Wires source maps, verifies locally, and checks readiness again | | Review, merge and deploy, then tell the agent |
| After the deploy, checks release health and one real issue's lineage | | Optional: connect Vercel or Cloudflare deploy markers in the repository's Runtime settings, **Sources** tab |

## When the agent can't create the key

The agent creates the key itself only when it can. It asks you to create the key instead when:

- you don't connect the Autter MCP server, or your agent has no MCP support
- your role in the organization is viewer
- your access token lacks the `mcp:write` scope. Reconnect the MCP server with write access, or create the key yourself
- agent key creation is turned off for your organization. An owner or admin can turn it back on in **Settings → Keys and tokens**

To create it yourself:

1. Open **Settings → Keys and tokens** and click **Set up a key**.
2. Choose **Send errors from my backend service**. For a browser-only app with no backend, choose **Catch errors in my frontend** instead.
3. Pick the repository this codebase maps to.
4. Set the key where the service runs (shell profile, gitignored `.env`, or secret manager) as `AUTTER_RUNTIME_KEY`.
5. Tell the agent the name of the variable. It never needs the value.

The agent keeps going with everything else while it waits. The key kind decides what it can do:

- **Server** (`autter_rt_…`): secret, for backends and relays. Keep it in environment variables and never commit it. Server keys send OTLP traces, metrics and logs.
- **Client** (`autter_rtc_…`): publishable, for browser-only apps with no backend. It works only from the exact origins you register, and it cannot send logs.
- **Upload** (`autter_rtu_…`): uploads and checks source maps, nothing else. Choose **Upload source maps from my build** for CI.

Runtime keys are separate from personal access tokens and MCP access tokens.

## Keep keys out of chat

When the agent creates a key, Autter shows it to the agent once. The agent pipes it straight into the secret store and names it afterwards only by its prefix. Do not paste a key into the agent chat: chat transcripts can be logged or shared. If you did, revoke the key and create a new one.

To revoke a key, open **Settings → Keys and tokens**.

## Set up operation logging

After installing the updated skills, ask your agent:

> Update this project's Runtime setup for structured logs and operation evidence.
> Check release and deployed support, preserve our existing logger, instrument
> checkout and background jobs, and verify stored logs and linked failure evidence.

The skills use `runtimeLogger` for diagnostics and explicit failed operation
outcomes or exception capture for issues. A returned callback defaults to
success; a payment rejection without a throw needs a declared outcome. The
APIs require Node/Next.js SDK and ingester **1.4.0+** ([compatibility table](/runtime/compatibility)), followed by an application
redeploy; updated skills alone do not provide that release.

See [Operation logging](/runtime/operation-logging) for the APIs, Node/Next.js
examples, OTLP logging in other languages, delivery limits, and verification.

## Set up endpoint regressions

Use the setup skills to inspect existing SDK initialization, update compatible packages, and configure request histograms and release identity. Node/Next.js examples opt into slow successful trace retention. External OTel exporters need explicit-bucket delta histograms.

Platform access does not change your deployed applications. Reuse their existing providers and deploy the required SDK configuration. Self-hosted ingesters need the versions in the [compatibility table](/runtime/compatibility). See [Endpoint regressions](/runtime/endpoint-regressions) for the complete setup, team feedback, and human review of draft fixes.

## Connect external logs

Ask `autter-runtime-setup` to connect your existing Sentry, PostHog, Datadog, AWS, Google Cloud, Grafana/Loki, Vercel, Cloudflare Workers, Bugsnag, Rollbar, New Relic or generic webhook source for the selected repository. The agent uses repository Runtime settings and checks stored records, analysis state and the actual draft PR URL separately. Connector-only setup does not require an ingest key or application SDK install. Read [External log sources](/runtime/external-sources) for provider credentials and automation policy.

## Updating or removing

Re-run the installer to pick up new skill versions. It replaces the older copies:

```bash
npx @autter/skills
```

To stop using a skill, delete its folder from your project's skills folder (for example `.claude/skills` or `.agents/skills`). Skills are just files; there is nothing to uninstall from a package manager. To disconnect the agent from Autter, remove the `autter` entry from `.mcp.json` or `.cursor/mcp.json`, and revoke its access token under **Settings → Keys and tokens**.
